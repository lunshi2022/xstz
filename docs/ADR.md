## ADR-017 · compileSdk 必须 37（本轮最重要的实测发现）

**问题**：原计划轨 B 用 `compileSdk 36`，实测编译直接失败：

```
Dependency 'androidx.compose.ui:ui-android:1.12.1' requires libraries and applications
that depend on it to compile against version 37 or later of the Android APIs.
:app is currently compiled against android-36.
```

**根因（依赖树已定位）**：

```
androidx.compose.ui:ui:1.12.1
└── org.jetbrains.compose.foundation:foundation-layout-android:1.12.1
    └── (由 Haze 2.0.1 的 KMP 变体传递引入)
```

Haze 是 **Kotlin Multiplatform** 库，其 android 变体依赖 **JetBrains Compose 1.12.1**，而 JetBrains Compose 1.12.1 与 androidx Compose 1.12.1 对齐映射，因此：

- BOM 2026.05.01 本应给出 `compose-ui 1.11.2`；
- 但 Gradle 的「取最高版本」规则让 Haze 拖进来的 1.12.1 胜出；
- 1.12.1 的 AAR metadata 声明 `minCompileSdk=37` → compileSdk 36 直接拒绝编译。

**结论**：

1. **compileSdk 37 是 Haze 带来的硬约束，与选哪条轨无关。** 除非放弃 Haze（等于放弃背景模糊，也就放弃了液态玻璃的核心），否则无法回避。
2. `compileSdk` 只是**编译期 API 级别**，不影响运行时行为与设备覆盖——那由 `minSdk 34` / `targetSdk 36` 决定。所以抬到 37 **无任何用户可见副作用**。
3. 曾考虑用 `resolutionStrategy` 强制降回 1.11.2，**放弃**：Haze 2.0.1 可能调用 1.12 的新 API，强制降级会在运行期崩溃，属于"编译期报错换成运行期崩溃"的负优化。

**维护含义（重要）**：

> **Haze 版本与 Compose 版本是耦合的。** 升级 Haze 会拉动 Compose 版本，进而可能再次抬高 compileSdk 下限。每次动 `haze` 版本号后，必须重新确认 `composeBom` 解析结果与 compileSdk 下限，不能只看 BOM 声明值。

## ADR-018 · 数据库加密：SQLCipher 整库 + Keystore 包裹随机 DEK

**背景**：方案 P0-2 记录旧版最严重的架构缺陷——用 `EncryptedDoubleConverter`
把金额做列级加密存成 TEXT，导致 `SUM(holdingQuantity * currentPrice)` 在
SQLite 侧对密文字符串做算术，静默返回错误值。REBUILD_PLAN 第 226 行确定
「数据库加密 = SQLCipher for Android，整库加密，保留 SQL 聚合/索引能力」。

**决策 1：加密形态 —— 整库加密，不做列级**

库文件整体由 SQLCipher 加密。列在 SQLite 眼里仍是普通 INTEGER/REAL，
`SUM` / `ORDER BY` / 索引 / `GROUP BY` 全部照常工作，DAO 层无需为加密做任何让步。
这是对 P0-2 的直接返修：问题根源不是"加密不够"，而是"加密的粒度错了"。

**决策 2：动的是哪个 artifact —— `sqlcipher-android`，不是 `android-database-sqlcipher`**

方案原文写的是 `net.zetetic:android-database-sqlcipher:4.7.2`，这个坐标+
版本组合**在 Maven Central 上不存在**（实测已确认）：

| artifactId | 最高版本 | arm64 `LOAD p_align` | 16KB 页合规 |
|---|---|---|---|
| `android-database-sqlcipher` | **4.5.4** | `0x1000` | ❌ |
| `sqlcipher-android` | 4.20.0 | `0x4000` | ✅ |

即：4.7.2 这个版本号是对的，但属于新 artifactId。选新库的决定性理由是
**16KB 页对齐**——方案风险表 T3 已预判「选 4.7+ 版本并核对其 16KB 支持」，
本次实测正是执行这一核对，结论与新库一致。旧库若被采用会直接违反
Play 2027-02 起对 64 位 native 库的要求。

**负面后果**：arm64 so 从 3.6MB 增至 5.2MB，release APK 体积上升（实测见状态文档）。
这是换取加密能力与上架合规的必然代价，无替代方案。

**决策 3：口令来源 —— Keystore 包裹的随机 DEK**

方案第 306 行给了两个选项「Keystore 包裹的随机 DEK，或用户口令派生」。
选前者：

1. 本地库每次启动要求输入口令，是把备份场景的交互成本错误搬到主流程——
   用户打开 App 就得输密码，是产品事故。
2. 随机 256 位 DEK 熵高于任何可记忆口令，不需要 KDF 拉伸，启动更快。
3. **与 ADR-008 不矛盾**：ADR-008 要求的是**导出文件**必须口令派生，
   因为文件要跨设备而 Keystore 密钥出不了设备。库文件不跨设备，
   两者场景不同，选型不同是正确的。

**负面后果（诚实记录）**：用户在系统设置里「清除凭据」或恢复出厂后，
Keystore 重建导致包裹密钥变更，DEK 再也解不出，库文件虽在但打不开。
此时**不能静默重建库**——那等于无声丢失用户资产数据，与拒绝
`fallbackToDestructiveMigration` 是同一条原则。实现上抛异常并提示从备份恢复，
且明确告知"不要卸载重装"（卸载会一并删库）。

**测试策略（受环境限制）**：SQLCipher 的核心是 native 库，Robolectric
无法加载（实测抛 `UnsatisfiedLinkError: nativeOpen`）。因此测试分两层：

- **JVM 层**（`KeyEnvelopeTest`，7 个用例）：封包格式、边界校验、AES-GCM 往返
- **设备层**（`SqlCipherAggregationTest`，4 个用例）：真实加密落盘、
  文件头非明文 SQLite、`SUM()` 聚合精确、错误口令打不开

第二条的「文件头非明文」断言是最后防线：若有人删掉 `openHelperFactory`，
所有功能测试仍会全绿（Room 用框架 SQLite 也能跑），只有这条会红。

## ADR-002 · minSdk 34（本轮收益最大的决策）

**决策**：`minSdk = 34`（Android 14+），`targetSdk = 36`（Android 16）。

**为什么它是收益而不是妥协**

| 能力 | API 要求 | minSdk 29 时 | **minSdk 34 时** |
|---|---|---|---|
| `RenderEffect` 背景模糊 | 31+ | 部分机型缺失 | **全设备可用** |
| AGSL `RuntimeShader` 折射 | 33+ | 部分机型缺失 | **全设备可用** |
| `ApplicationExitInfo` | 30+ | 可用 | **可用（支撑 ADR-009）** |

**直接后果：玻璃降级矩阵由四档缩为三档**，占原 18% 的 `L1 Tint`（只有染色、无模糊，最"不像 iOS"的一档）彻底消失。视觉目标因此从 88~92% **上调至 92~95%**。

**代价**：设备覆盖从约 97% 降至约 45%。自用 + 开源分发，接受。

**附带简化**：`androidx.core:core-splashscreen` 依赖可移除（splash attrs 为 API 31+，34 原生可用）。

## ADR-003 · 分发渠道：开源仓库 + GitHub Release

**决策**：不走任何应用商店，通过 GitHub 仓库源码 + Release 分发 APK。

**理由**：原项目 0 star / 0 fork / 唯一 Release 下载 2 次，无商业分发迹象。此路径**免掉**工信部 App 备案、软著登记、商店隐私检测报告三项合规工作，工期直接省 1~2 周。

**负面后果**（必须知情）：

1. **签名成为单点故障**——没有商店代持密钥。keystore 丢失 = 永远无法覆盖升级，只能让用户卸载重装并丢失数据。必须离线双份备份。
2. **无外部质量把关**——商店的兼容性测试、崩溃率监控都不存在。崩溃只能靠用户主动反馈（这也是 ADR-009 导出诊断包存在的原因）。
3. **国内下载受限**——GitHub 直连不稳，需在 README 提供镜像或说明。
4. **仍建议保持 targetSdk 36**：虽然当前不需要过审，但 Play 对 2026-08-31 后上架的应用要求 ≥36；保持 36 可让"日后想上架"这条路不被堵死。

## ADR-004 · 无存量数据，取消一切迁移逻辑

**决策**：不实现旧库（`AppDatabase` v6）→ 新 schema 的迁移，不做迁移向导、不做迁移回退。

**理由**：用户确认无真实存量用户数据。迁移是整个项目里最贵、最容易出数据事故的部分（约 1 周），无数据则无必要。

**负面后果**：

1. **旧版导出的 JSON 备份不再可导入**——旧备份用本机 Keystore 密钥加密，新实现用口令派生密钥（ADR-008），两者不兼容。
2. **不可逆**：一旦新版发布后发现有用户数据，补救成本极高（需重写迁移并让用户先装旧版导出）。
3. **因此需要在阶段 1 第一天做一次实证**：装一次旧版、确认库里确实没有需要保留的记录，把"没有数据"从声明变成已验证事实。这一步只需 10 分钟，但不做就是纯假设。

## ADR-006 · 视觉验收口径：观感对齐，不做逐像素复刻

**决策**：以「观感与交互语言对齐」为验收标准，**不做**逐像素截图比对，**不做**陀螺仪倾斜高光伪实现。目标值：`L3` 档 **92~95%**（加权 93.9%），`L2` 档 85~88%。

> 初定时为 85~90%；`minSdk 34`（ADR-002）消掉 `L1 Tint` 档后上调。

**理由**：Liquid Glass 有三项在 Android 上原理性不可达——系统级统一光场（决定高光随姿态流动）、`GlassEffectContainer` 的形状融合、跨 App 的材质一致性。逐像素对照的工期会翻倍到 3 周以上，且最终仍有约 10% 做不到。而「像不像 iOS」在实际观感中的权重，主要落在圆角曲率、材质参数、边缘高光、动效曲线这四项——这四项都可达成。

**负面后果**：

1. **验收留有主观空间** → 用 `docs/VISUAL_ACCEPTANCE.md` 的六维度加权 + 6 条一票否决红线量化，每个维度给出可复现的测量方法（如圆角用 45° 对角线 `d/r` 比值判定），把"感觉像"变成"测得出来"。
2. **高光不随姿态响应**，静态观感几乎无影响（只在倾斜设备时明显），约损失总分 2.1%，登记为"已知并接受"。
3. **必须有一台 L3 设备**才能实测 92% 档；只有 L2 机则只能按 85% 验收，L3 靠代码审查推断。

## ADR-007 · 包名沿用 `com.huaying.xstz`（不可逆）

**决策**：不改包名。

**理由**：改名需全局重命名 namespace、目录结构与所有模块的 `build.gradle.kts`，在无存量数据的窗口期虽可做，但用户选择省掉这次操作。

**三条负面后果（已告知，用户知情接受）**：

1. **同包名 + 不同签名无法覆盖安装** —— 旧版用 debug 签名，新版若用正式签名，二者签名不同，Android 会拒绝覆盖，用户必须先卸载（数据随之丢失）。
2. **未来上 Google Play 会被要求证明 `com.huaying` 前缀的域名或商标权利** —— 而这个前缀来自原作者，届时包名已不可改。**这是唯一可能真正卡住的情形。**
3. **开源发布易被误认为原项目的官方分支** —— 需在 README 显式声明"非官方、与原仓库无关联"。

**结论**：当前分发方式为 GitHub Release（ADR-003），第 2 条不成立。若未来规划里出现过"上架商店"的念头，这是唯一需要重新考虑的地方——现在改成本接近零，以后是无穷大。

## ADR-008 · 备份加密：口令派生密钥（Argon2id）

**决策**：导出备份用用户口令派生密钥加密（Argon2id），而非明文 JSON，也不再使用本机 Keystore 密钥。

**理由**：明文落盘财务数据是隐私风险。而旧实现的致命缺陷正在这里——用本机 AndroidKeystore 密钥加密，而 Keystore 密钥**不可导出**，导致备份文件换机、重装、恢复出厂后**永久无法解密**。这不是安全设计，是功能失效。

**负面后果**：

1. **口令丢失 = 备份永久不可解**。设置页必须强提示，导出后强制确认"已记下口令"，且明确写"忘记无法找回"。
2. **Argon2id 需要实现来源**：`argon2kt`（native）或纯 Kotlin 实现。若用 native，需核对 16KB page size 对齐（Play 2027-02-01 起的要求），且会增加包体。
3. **导入导出有耗时**：Argon2id 参数若设得高（如 m=64MB, t=3），低端机上单次派生约数百毫秒到 1 秒，需放后台线程并显示进度。

## ADR-009 · 零第三方崩溃 SDK

**决策**：不接 Bugly / Firebase / Sentry，用系统能力自建。

**理由**：Firebase Crashlytics 依赖 GMS，国内不可用；Bugly 需注册云账号且对个人开发者不友好；Sentry 自托管有额外运维成本。而 minSdk 34 让官方方案完全够用。

**实现**：

1. `ApplicationExitInfo`（API 30+）读取历史崩溃原因、时间戳、ANR 堆栈，**无需任何权限**；
2. `Thread.setDefaultUncaughtExceptionHandler` 捕获未处理异常，写入本地环形日志（保留最近 50 条）；
3. 设置页「导出诊断包」：打包崩溃日志 + 设备信息 + 最近操作记录为 zip。

**收益**：零合规负担、零额外权限、零包体增量、开源用户无隐私顾虑。
**代价**：不能自动上报，需用户手动发诊断包。
**扩展性**：抽象 `CrashReporter` 接口，默认实现为本地；将来若需自动上报，替换实现即可，不动业务代码。

## ADR-010 · 图表全部自绘

**决策**：收益走势图、资产配置饼图**全部自绘 Canvas**，移除 Vico。

**收益**：少一个依赖、包体更小、图表圆角裁切与玻璃材质完全统一（Vico 做不到这一点，它的绘制层不接受外部 Shape 裁切）。

## ADR-011 · 仅简体中文，但资源结构按可国际化设计

**决策**：只提供简体中文文案；但所有字符串走 `stringResource`，不硬编码。

**理由**：原项目 `stringResource` 使用 **0 处**，200+ 条 `strings.xml` 完全闲置，中文全写死在 Kotlin 里——这是维护问题，与做不做英文无关。消灭硬编码是必须的，做英文是可选的。

**负面后果**：

1. **阶段 3 每页文案需二次搬运**（从 Kotlin 字面量搬到 `values-zh-rCN/strings.xml`），增加约 2 天工作量，且容易漏。
2. **开源受众受限**：非中文用户无法使用，会降低开源项目的潜在贡献者数量。
3. **单一 `values-zh-rCN` 目录**意味着系统语言为英文时回退到默认 `values/`——需把默认资源也放中文，否则会出现英文系统下显示空白的低级错误。

## ADR-012 · 行情数据源：接口抽象 + 腾讯为默认实现

**决策**：定义 `FundQuoteSource` 接口，腾讯 `qt.gtimg.cn` 作为默认实现；解析器保持**纯函数**以便单元测试。

**理由**：腾讯接口是**非官方公开接口**，随时可能变更字段顺序、增加校验、限流或下线。写死进 Repository 等于把项目寿命绑在一个不受控接口上。

**负面后果**：

1. **抽象层增加一层间接**：调试时需多跳一次才能看到实际请求；对只有单一实现的项目，这层是"为未来付费"。
2. **接口仍可能变**：抽象只能降低替换成本，不能防止接口下线。需保留"手工录入净值"作为兜底路径（原项目已有此功能，必须保留）。
3. **18 个字段索引的解析逻辑必须带回归测试**：原项目 `TencentApiParser` 有 17 个测试，这是搬迁时优先保留的资产之一。

## ADR-013 · 移除 Material You 动态取色

**决策**：不读壁纸取色，使用固定的语义色令牌（含深色主题）。

**理由**：动态取色会让界面主色随壁纸变化，与玻璃材质依赖的"统一光感"直接冲突——玻璃的通透感需要稳定的背景明度关系，而 Material You 可能给出任何色相的容器色。

**负面后果**：

1. **失去系统级个性化联动**：Android 用户习惯的"App 跟随壁纸"体验消失。
2. **需自建主题色选择**（若要做）：至少提供 2~3 套预设色调，否则用户无任何个性化空间。
3. **与 Android 设计规范有偏离**：Google 官方鼓励动态取色，这是有意为之的取舍，需在 README 说明理由，避免被当作"没适配"。
